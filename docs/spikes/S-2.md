# S-2 · Session capture, token lifetime, unattended refresh

**Card:** T-08. **Status:** stage 2 done for steps a-c. Step d (the two-day logged-in check) is **pending**; the verdicts hold under either outcome.

## Question

The extension never stores the user's password. It reuses the login the user already has. How long that session lasts, and whether it can be renewed with nobody present, decides whether unattended sniping is possible.

## What is known before the measurement

From planning notes and S-1 recon. None of it is measured on a real account yet; ⚠ means unverified.

- The site sends `Authorization: Bearer <JWT>` (HS256) to `buyerapi.shopgoodwill.com`. Claims reportedly include BuyerId, IpAddress, a browser/UA claim and `exp` ⚠.
- The session also lives in an AES-obfuscated JS cookie `cookieSession_8`, default expiry 1 day, `SameSite=Strict` ⚠.
- `SignIn/RefreshToken` takes `{refreshToken, clientIpAddress}` (`SGW_ENDPOINTS.refreshToken`, evidence: bundle). `SignIn/RevokeToken` also exists.
- One leaked sample had `exp` about 30 days after capture ⚠. That may mean the JWT outlives the 1-day cookie, which is the best case for us.

## Method

1. `scripts/jwt-claims-only.ts` (new): decodes a JWT locally from stdin, with no signature check, no network and no file writes. It prints only claim names, `iat`/`exp` as ISO dates, `exp - iat` in hours and days, and yes/no for IP-like and Browser/UA-like claim names. It prints no other value and never echoes the token or quotes bad input. Tested in `test/unit/scripts/jwt-claims-only.test.ts`.
2. The user follows `docs/USER-STEPS/S-2.md` while logged in, in their normal browser. The worker makes no request to SGW, never logs in, and never reads the browser profile or cookies.
3. Binding (criterion 4) is documented from claim names only. Nothing is spoofed.

## Capture options and permission cost

Architecture §1.5 chose a MAIN-world observe-only "api-tap", with `webRequest` as fallback. This analysis is from code knowledge; the USER STEP supplies the evidence that the header exists at all.

| | MAIN-world tap | `webRequest` |
|---|---|---|
| Manifest | `content_scripts` entry, `world: "MAIN"`, `run_at: "document_start"`, matches `https://shopgoodwill.com/*` | `webRequest` in `permissions`, plus host permission for `https://buyerapi.shopgoodwill.com/*` (already needed) |
| New permission string | None. The `shopgoodwill.com` host permission is needed anyway | One: `webRequest`, on both browsers. `permissions-snapshot` changes |
| Install warning | No new one | None expected for non-blocking use ⚠ (verify in the built manifest) |
| Min browser | Chrome 111, Firefox 128 | Any |
| Sees `Authorization` | Yes, if the page sets it through `fetch` or `XMLHttpRequest.setRequestHeader` (Angular `HttpClient` uses XHR). The wrapper must be installed before app code runs, hence `document_start` | Yes, in `onBeforeSendHeaders` with `requestHeaders`. Chrome may need `extraHeaders` ⚠. Non-blocking, so no `webRequestBlocking` |
| Sees response bodies (needed to catch a refreshed token) | Yes, by cloning the response | **No.** webRequest cannot read bodies |
| Sees request bodies (`RefreshToken` field names) | Yes | Only raw bytes in `onBeforeRequest`; workable but clumsy |
| Also feeds "reuse before fetching" listing data | Yes | No |
| Misses | Requests from a worker or a frame the script is not injected into; code that cached the original `fetch` before the wrapper; the page can forge messages, so the isolated side must validate sender and shape | Nothing by origin; sees every request from any context |
| Page-visible footprint | Patched `fetch`/XHR prototypes are detectable by the page; the tap must be strictly observe-only | None |

Other options, not pursued:

- `cookies` permission to read `cookieSession_8`: needs decrypting an obfuscated blob and couples us to the site's constant. Kept only as a fallback to evaluate if both above fail.
- Asking the user to paste a token: rejected in §1.5.

Expected outcome: the tap wins on permission cost (zero) and on body access (needed for a refresh token). `webRequest` wins only if the header turns out to be set from a context the tap cannot reach. Criterion 1 decides.

## Decision rule for `SgwSession`

Stage 2 applies these mechanically.

**Refresh token**

- Store the refresh token **only if unattended refresh is proven**: criterion 3 shows (a) the tap can read a refresh token, (b) the request body needs only values the background can supply (the token and `clientIpAddress`), and (c) a token obtained that way works after the cookie's 1-day expiry with no user present.
- If any of (a)-(c) is unproven or fails, `SgwSession` holds **no refresh token**: `refreshToken: null`, access token only, in `storage.local`.
- A stored refresh token goes in `storage.local`, is never logged, and is removed on disconnect.

**Expected unattended validity window** is the shortest of:

- the measured `exp − iat` (criterion 2);
- the observed day-1 / day-2 login persistence (criterion 3, step d), if shorter;
- if an IP claim exists, the time until the user's IP changes. That is unknown; record it as a risk, not a number.

**Graceful degradation if the window is under 24 h** (or the refresh path is unproven and the token is short):

1. Sniping is limited to bids whose end time falls inside the known-valid window. Later bids are not promised.
2. For a bid beyond the window, the app queues it and tells the user at queue time the latest end time it can honor, and why.
3. An overnight job still searches, queues favorites and notifies. It does not claim to snipe.
4. A 401 mid-window sets `SgwSession` to `expired`, cancels scheduled snipes with a notification asking the user to open SGW once (the tap re-captures the token from normal browsing), and does not retry in a loop.
5. The plan's reliability tiers are re-read against this window before any "sleep-safe" claim reaches UI copy.

If the window is 24 h or more but unattended refresh is not proven, the same path applies to bids beyond the window.

### Decision (applies the rule above)

- **Refresh token: no.** Conditions (a)-(c) of the rule are unproven. `SgwSessionRecord.refreshToken` stays unused.
- **Expected unattended validity:** nominally about 30 days from login (`exp`). Effective validity is the shorter of `exp` and the first moment SGW rejects the token for any reason (IP/UA change, logout, newer login). Treat 30 days as an upper bound, not a promise.
- **Step d, either way:** the extension sends the bearer with `credentials: 'omit'` (architecture §1.7), so the site's 1-day cookie does not gate API calls unless the server cross-checks it. If d shows the site logging the user out after a day, the bearer may still work; the T−24 h authenticated read (below) is the real test, not the cookie. If d shows the user staying logged in for 2+ days, that mildly supports the 30-day figure. Neither outcome changes the design.
- **Degradation (<24 h) path:** as in the rule above. It is triggered by an observed rejection, not by `exp`.

### Recommendations for T-28 (SessionAdapter) and T-83 (preflight)

1. **`exp` is the only timing claim.** `observe()` derives `expiresAt` from `exp` alone and never requires `iat`. Read only `BuyerId` and `exp` from the payload; never store, log or message other claims (`BuyerSession`, `MobRegistrationToken`, `jti` are session secrets).
2. **'expiring' threshold: 72 h (3 days)**, not 12 h. With no refresh, only the user can renew, and the user may be away; 12 h is too late to ask. Notify at 72 h, 24 h and 1 h before `exp` (R3 already has the last two). 'expiring' still allows writes (I-08). One named constant.
3. **Snipe horizon guard:** an auction ending after `expiresAt − 15 min` is not promised; the UI says so when the snipe is armed. Pure `exp` arithmetic, no network.
4. **Rejection means 'expired'.** Any authenticated call that gets HTTP 401 or `isUnauthorized: true` (`SgwApiError('auth')`) sets state `expired` immediately, with no retry loop, and raises one user alert: "ShopGoodwill rejected the saved login. Open shopgoodwill.com and sign in; ShopBadwill will pick up the new session." The cause is unknown (IP, UA, logout, expiry), so the text names none. A later `observe()` of a token for the same `BuyerId` returns the state to 'ok'. Snipes scheduled after the rejection are marked at risk.
5. **Detect binding early, not at fire time.** T-83 makes one cheap authenticated read (an `auth: 'required'` GET through the `background` lane) at **T−24 h** and **T−1 h** before every armed snipe, in addition to the T−15 min preflight. A rejection at T−24 h leaves a day for the user to fix it. Do not compare IPs locally: the extension has no IP source, and an IP-lookup service would be a new network dependency.
6. **UA change:** after a browser update (`runtime.onInstalled` with reason `browser_update` on Firefox, `chrome_update` on Chrome ⚠ verify) mark the session "revalidate" so the next opportunity makes an authenticated read, instead of waiting for T−24 h.
7. **Snipe lane:** never retry or refresh at fire time. An auth failure there goes to the fallback policy and the outcome is reported honestly.

## `SgwSession` contract note

Checked against `src/ports/sgw-session.ts` and `SgwSessionRecordSchema` (`src/domain/types.ts`). Contract files were not edited.

**Consistent, no change:**

- `observe({bearer, capturedAt, source})` with `source: 'tap' | 'webRequest'`.
- `current()` returning `{bearer, expiresAt, buyerId}`.
- `refresh(): Promise<boolean>`, documented "only if S-2 enabled refresh". S-2 did not, so T-28 always resolves `false` and never calls the network.
- `SgwSessionRecord.refreshToken` is optional: leave it unset (do not remove it; the schema is frozen).
- States `ok | expiring | expired | logged-out` cover everything above (rejection = `expired`).

**Not consistent: proposed changes**

1. **Threshold (comment and constant only; no type change).** `src/ports/sgw-session.ts` and `src/domain/types.ts` say `'expiring' = less than 12 h left`. Change both comments to `less than 72 h left`, and have T-28 export `SESSION_EXPIRING_MS = 72 * 3_600_000`. Why: without refresh the user is the only renewal path, and 12 h is too short a warning. Any test that encodes 12 h needs the new value.
2. **`observe` doc comment.** Add: "`expiresAt` comes from the JWT `exp` claim; SGW tokens have no `iat`, so it must not be required. Only `BuyerId` and `exp` are read from the payload."
3. **One new method.** Add `reportRejected(): Promise<void>` to the port: sets state `expired`, no network. Why: recommendation 4 needs `SgwApi` (T-26) to tell the session about a 401 or `isUnauthorized`, and the API adapter should depend on the port, not on T-28's class. If the coordinator prefers no port change, T-28 can expose it on the class and wire it by injection; the behavior is the same.
4. **Optional, no port change.** A "revalidate" marker (recommendation 6) can live in T-28's own `sbw:` storage.

**Open until d is reported:** nothing in the contract depends on d. If d, or later evidence, shows the site refreshes unattended, revisit criterion 3 and `refresh()`.
