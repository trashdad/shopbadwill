## Run it

```
python -m pip install -r test/e2e/firefox/requirements.txt -c test/e2e/firefox/constraints.txt   # once (a venv is best; SBW_PYTHON=<venv python>)
pnpm test:e2e:firefox                                         # build:test + pytest
pnpm test:e2e:firefox --no-build -k badge                     # reuse the build, filter
```

`test/e2e/firefox/run.ts` builds the Firefox test extension (`pnpm build:test -b firefox --mv3`), finds Python (`SBW_PYTHON`, else `python3`/`python`, or `python`/`py -3` on Windows), checks the harness dependencies, and runs pytest in `test/e2e/firefox/`. Extra arguments go to pytest. A filter that selects nothing exits 5, so a mistyped gate fails.

Environment: `SBW_FIREFOX_BIN` (default: the standard Windows install, else `firefox` on PATH), `SBW_GECKODRIVER` (default: `$GECKOWEBDRIVER/geckodriver` on GitHub runners, else Selenium Manager), `SBW_E2E_HEADED=1` (default headless).

## How it works

1. **Build.** The test build lands in `.output/firefox-mv3-test`, not `.output/firefox-mv3` as the plan text says. `build:test` uses mode `test`, so a test build never overwrites the production build that `check:prod-bundle` scans. Its manifest is the production manifest plus the `http://127.0.0.1/*` host.
2. **Fixture site with a hostname override** (`harness/sgw_site.py`). Firefox's proxy prefs send all http and https traffic to a local proxy on `127.0.0.1:<random>`. A `CONNECT shopgoodwill.com:443` is answered locally: the proxy terminates TLS with a throwaway self-signed EC certificate, generated per run and never written to the repo. Firefox runs with `acceptInsecureCerts`. The proxy then serves `test/e2e/firefox/fixtures/sgw/`. Every other host gets 403, and the proxy never opens an outbound connection, so **no request can reach the real shopgoodwill.com or any other internet host**. Firefox's own background traffic (remote settings) is refused the same way. Loopback is not proxied (`network.proxy.allow_hijacking_localhost=false`, Firefox's default), so `pnpm fake:sgw`/`fake:google` stay directly reachable. See **Network sandbox** below for how a proxy bypass is prevented and detected.
   - Why not add `http://127.0.0.1/*` to the content-script `matches` in test builds? It would change the test build's permission surface. `test/unit/manifest-permissions.test.ts` asserts that a test build is production plus exactly one host permission, so it would fail. With the override, the content script runs under its real match (`https://shopgoodwill.com/*`), and `wxt.config.ts` is unchanged.
3. **Firefox** (`harness/firefox.py`): headless, fresh profile, `extensions.webextensions.uuids` pins the add-on's internal UUID to `5bad0111-0000-4000-8000-000000000006`, so extension pages have fixed `moz-extension://` URLs. geckodriver runs with `--allow-system-access` (needs geckodriver ≥ 0.36; see below).
4. **Install**: `driver.install_addon(".output/firefox-mv3-test", temporary=True)`, the same as about:debugging. The returned id must equal the manifest's gecko id. Host permissions and the content script are active at once; no grant step is needed.
5. **Assertions** (`smoke_test.py`):
   - `test_badge_shadow_dom_on_fixture_page`: load `https://shopgoodwill.com/`. Check that the page is the fixture (URL, title, and the proxy's request log), then that `<shopbadwill-badge>` has a shadow root containing a non-empty `[role="status"]`. Mutation check: without the add-on, it times out with "no `<shopbadwill-badge>` host".
   - `test_background_answers_sbw_test_state`: calls `sbw:test:state` and checks the dump's shape.
   - `test_reconcile_created_the_tick_alarm`: `sbw:test:state` lists exactly one `sbw:tick` alarm, every 2 minutes.

   The last two are strict xfails, each keyed on the built `background.js`. The state check becomes a plain, required test once the build contains `sbw:test:state` (the hooks are wired). The reconcile check becomes required once the build also contains `sbw:tick`. Until then, they report XFAIL with the reason. Verified with a temporary, uncommitted background edit: with `installTestHooks({ browser })` wired in, the state check passed for real. After also creating `sbw:tick` there, all three passed.

## Network sandbox (fix round 1)

`acceptInsecureCerts` is only safe while every request goes through the proxy. If Firefox went around it, real traffic would flow without certificate checks. The sandbox is enforced twice (`harness/firefox.py`):

- **Prefs (`proxy_prefs`).** These close every route around the proxy. Manual proxy for http and https, with no shared or backup copies. `network.proxy.failover_direct=false`. SOCKS, FTP, the PAC URL and `network.proxy.no_proxies_on` are reset to empty. DNS-over-HTTPS (`network.trr.mode=5`), HTTP/3 (QUIC), WebRTC, DNS prefetch, link prefetch and speculative connections are off. Captive-portal and connectivity checks are off too. Only loopback stays direct (`allow_hijacking_localhost=false`), for the fake servers; it cannot leave the machine.
- **Canary (`check_sandbox`).** Every new browser runs it before any test navigation and before the add-on is installed. It loads `https://example.invalid/` and `http://example.invalid/` (`.invalid` never resolves, so even a bypass could not reach a server). It then requires two things:
  1. The proxy's refusal log has `example.invalid:443` and `GET http://example.invalid/`.
  2. The browser shows only a refusal. For https that is a network error page (Marionette: *Reached error page: about:neterror?e=proxyConnectFailure*). For http it is the proxy's own 403 page, which carries the marker `sbw-e2e-proxy-refused`.

  Anything else, including an unexpected navigation error, raises `SandboxError`, and `conftest.py` stops the whole run with `pytest.exit(..., returncode=3)`. Verified by setting `network.proxy.type=0`: the run aborted before any test, with *canary https://example.invalid/ never reached the E2E proxy…* and exit code 3.
- **Tests.** `sandbox_test.py` runs without Firefox: abort logic against a fake driver, the prefs, and the proxy's refusals over raw sockets. `smoke_test.py::test_sandbox_canary_was_refused_by_the_proxy` checks that the canary ran for the real browser.

Python dependencies are pinned in full. Direct pins are in `requirements.txt` and every transitive one in `constraints.txt`. In CI, `check_pins.py` fails if any package in the dependency closure (extras included, e.g. `urllib3[socks]` → PySocks) is unpinned or installed at another version.

## Test hooks (`src/test-hooks/`)

`installTestHooks({ browser })` (`index.ts`) is a no-op unless `import.meta.env.SBW_TEST`. In a test build it loads every other `src/test-hooks/*.ts` module through `import.meta.glob` (eager) and calls each module's `install(ctx)`. It then registers one `runtime.onConnect` listener for Ports named `sbw:test:*`:

```js
// from any extension page (the harness uses the Firefox sidebar page in a background tab)
const port = browser.runtime.connect({ name: 'sbw:test:state' });
port.onMessage.addListener((reply) => { /* { ok: true, value } | { ok: false, error } */ });
port.postMessage({ payload });   // one request per Port; the background replies and disconnects
```

- **Ports, not `runtime.sendMessage`**: test traffic never reaches T-35's `onMessage` router, which validates envelopes and may answer a malformed message with an error envelope. Two `onMessage` responders would race. Other `onConnect` listeners (`sbw:job-progress`, `sbw:snipe-countdown`) must ignore names they don't own. The hook listener ignores every non-`sbw:test:` name.
- **Only this extension's pages** may call a hook (`sender.id` and `sender.url` are checked). A content script on a web page gets `{ ok: false }`.
- **No `wxt/browser` import** in `src/test-hooks` (PLAN §2.1 forbids it there). The background passes its `browser` in. `TestHookBrowser` is the typed slice the hooks use; a unit test checks at compile time that WXT's `browser` satisfies it. A new hook that needs more of the API adds it to that interface.
- **Wiring (T-36)**: at the top level of the background, synchronously, so the Firefox event page has its listener before it handles the waking event: `if (import.meta.env.SBW_TEST) installTestHooks({ browser });`. Hook modules must have no top-level side effects. Verified: with that line in the T-01 placeholder background, both production builds stayed at 630 B with no `sbw:test`, `installTestHooks` or `SBW_TEST` in the output, and `check:prod-bundle` passed.
- **New hooks** (T-39 `base-url`, T-59 `advance`/`fire-alarm`, T-72 `google-auth-stub`): add `src/test-hooks/<name>.ts` exporting `install(ctx: TestHookContext)`, and call `ctx.serve('sbw:test:<name>', handler)` if tests call it. A module without `install` makes `installTestHooks` throw, so the mistake shows up at the first test-build start.
- `sbw:test:state` returns `{ installedAt, hooks, storage: { local, session }, alarms }`. `installedAt` resets whenever Firefox restarts the event page.

## What is and isn't reachable from WebDriver in Firefox

Probed against Firefox 157.0.1 with the test build installed.

| Target | Reachable? | How / why not |
| --- | --- | --- |
| Background service worker | **No** | Firefox MV3 has no extension service worker; the background is an event page (`background.scripts`). WebDriver exposes no target for it, unlike Chromium's `context.serviceWorkers()`. |
| Background event page as a WebDriver window | **No** | It is not a browsing context that classic WebDriver or BiDi can switch to. |
| Background `Window` via `runtime.getBackgroundPage()` | Partly | From an extension page it resolves to `moz-extension://<uuid>/_generated_background_page.html`. The bundle's globals are not visible through WebDriver's sandbox: `typeof w.background` is `undefined`. Don't rely on it; use a test hook. |
| Background state | **Yes, via hooks** | `sbw:test:*` Ports from an extension page (`Extension.call_hook`). |
| Extension pages (`moz-extension://…/sidebar.html`) | **Yes, with system access only** | Without `--allow-system-access`, both `WebDriver:Navigate` and BiDi `browsingContext.navigate` fail: *Navigation to "moz-extension://…" is not allowed in this context*. With it, navigation works and scripts there see `browser.*`. |
| `browser.storage`, `browser.alarms`, `browser.permissions`, `runtime.getManifest()` | Yes | From an extension page via `execute_script` (returned promises are awaited). Verified: `storage.local.get(null)`, `alarms.getAll()`, and `permissions.getAll()` (origins = the 3 manifest hosts, granted at temporary install). |
| Sidebar panel (`sidebar_action`) as a sidebar | No | Browser chrome UI. Load `sidebar.html` in a tab instead. |
| Content script's isolated world | No | `execute_script` on a web page runs in the page's world (`typeof browser` is `undefined` there). Assert on the DOM the content script produces. |
| Content-script Shadow DOM | Yes | `element.shadow_root` (WXT's `createShadowRootUi` uses `mode: 'open'`). |
| Browser chrome context | Yes, with system access | `driver.set_context("chrome")` runs privileged JS (`Services.prefs`, …). Not used by the harness; an escape hatch. |
| Extension console output | No | Classic WebDriver has no log endpoint for extension contexts. Use a hook, or the about:debugging inspector when running headed. |
| Time travel / firing alarms | Not yet | Comes with T-59's `sbw:test:advance` / `sbw:test:fireAlarm` hooks over the same Port mechanism. |

## CI (`.github/workflows/ci.yml`, job `e2e-firefox`)

Steps: `actions/setup-python@v5.6.0` (3.14, pip cache keyed on `requirements.txt` and `constraints.txt`), then `pip install -r requirements.txt -c constraints.txt` and `check_pins.py`. Next it prints the Firefox and geckodriver versions, starts the fake servers, and runs `pnpm test:e2e:firefox`. Failure screenshots and page sources from `test-results/firefox/` and the fake-server logs are uploaded as `firefox-e2e`. The runner's Firefox and `$GECKOWEBDRIVER/geckodriver` are used.

Linux risks not yet verified on a runner: geckodriver older than 0.36 would reject `--allow-system-access`. A snap-packaged Firefox can't read profiles under `/tmp` (GitHub's image installs Firefox from Mozilla's apt repository, not the snap). `continue-on-error: true` stays until a green run on GitHub; then remove it so the job is required (§7.3).
