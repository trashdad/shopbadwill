Card T-13. Status: **closed**. Evidence comes from three runs against the local fake SGW server on 2026-10-08, with no traffic to shopgoodwill.com. Raw data is in `scripts/timing-probe/results/`.

**Firefox host verdict: the runner-page fallback (T-116) is REQUIRED, for timer precision, not for liveness.** The event page *can* be held alive: `getPlatformInfo` heartbeats worked 21/21. But while no extension window is open, Firefox defers timers by about `min(delay/8, 10 s) − 0.6 s` (its `TimerThread` firing-delay tolerance, confirmed by the pref run), which is 6.8 s for the T−60 timer. Single, staged and Worker timers were all deferred together, so no in-page timer technique fixes it. An unfocused extension popup (`windows.create({type:'popup', focused:false})`), open from T−60 to the post-read, removed the deferral for every timer in the extension, including the event page's own. T-116 therefore moves into Phase 4 as **not conditional**, per §15 Q2. Its job is to keep an extension window open across the fire. The timer itself can stay in the background.

## Method

### What runs

A throwaway probe extension (`scripts/timing-probe/ext/probe.js`, never shipped, outside `src/`) runs the snipe timer of architecture §1.3 end to end, as a dry run against the local fake SGW server. Each **lane** is one installed copy of the probe. It runs N **cycles** back to back. Every cycle is one scheduled dry-run fire:

1. **Arm.** `alarms.create('wake:<n>', {when})` at `fireAt − 5 min`. A synthetic auction end `E` is set in *server* time, and `fireAt = E − lead(8 s) − oneWay`.
2. **Wake.** The alarm usually wakes a dead worker or event page (cold start). The time `onAlarm` runs, minus `alarm.scheduledTime`, is the **wake latency**.
3. **`KeepAlive.hold()`.** `setInterval(runtime.getPlatformInfo, 20 s)`. No network request is involved.
4. **Clock offset.** Three `ItemDetail` reads 20 s apart. The probe keeps the lowest-RTT sample: `offset = serverTime − (t0 + t1)/2` and `oneWay = rtt/2`.
5. **Verify read at T−60 s**, then the **tight timer** to `fireAtLocal = E − lead − oneWay − offset`, measured three ways in the same cycle:
   - **Timer A** is §1.3 as written: one `setTimeout(fireAt − now)` from T−60. It only records when it ran.
   - **Timer B** is staged hops: `setTimeout` for ¾ of the remaining time, repeated until ≤ 20 ms remain, then a final hop. B triggers the dry-run PlaceBid.
   - **Timer C** (Firefox only; Chrome service workers cannot create workers) runs the same deadline in a dedicated `Worker`, off the event page's main thread. It only records.
6. **Fire.** The probe persists `attempt.sentAt` in `storage.local` (the idempotency rule), then sends `POST ItemBid/PlaceBid` with a **20 s `AbortController`**. The fake stalls PlaceBid for **25 s**, so every fire is a "20 s stalled fetch" ending in an abort. A post-read follows.
7. **Hold** until `fireAt + 90 s`, so the hold lasts **≥ 6.3 min** from wake. Then **release**: heartbeats stop, the recovery alarm is cleared, and the next cycle is armed 90 s out.
8. **Restart path.** A `recover:<n>` alarm at `fireAt + 100 s` is cleared on release. If the worker died, the alarm wakes a fresh instance. That instance reads the persisted state: if `sentAt` is set without a result, the outcome is **ambiguous**, and it does a post-read before deciding. Otherwise it reports a missed fire.

Every step is reported by `fetch` (text/plain) to a small collector in `run.ts`, which writes `events.jsonl`. A **tick** report every 5 s, using `fetch` only and no extension API, shows when an instance stopped running. Each instance has a random id, so a restart shows up as a new id. Ticks pause from the verify read until timer A has fired, so the probe's own timers do not sit next to the timers under test.

**Built-in positive control.** After release there are no heartbeats, only ticks. If the idle kill is active in this setup and reporting `fetch`es do not keep the background alive, the ticks must stop about 30 s after the last API call, and the next wake must be a cold start (new instance id). Every cycle checks this, and it held in every cycle on both browsers (see Results).

**Control lanes** (3 cycles each per browser, against a second fake whose PlaceBid stalls 45 s):
- `longfetch`: heartbeats on and a 60 s abort, so the fetch stays open for 45 s. Tests whether a fetch longer than 30 s alone kills the worker.
- `hbstop`: heartbeats stop at the fire, with a 45 s stall. This forces a death mid-fetch and exercises the restart path with `sentAt` set.

**Follow-up runs (Firefox only).** Both were added after run 1 showed the Firefox deferral:
- **Runner study** (`run.ts --runner-study`). Two lanes open an unfocused extension popup (`runner.html`, the T-116 shape) at T−60 that runs its own timers A and B. A third, baseline lane opens no popup. Timing is shorter: wake at T−110 s, verify at T−60 s, 6 cycles per lane. It ran concurrently with run 1.
- **Pref confirmation** (`run.ts --browsers firefox --ff-pref timer.maximum_firing_delay_tolerance_ms=0.0 --ff-pref timer.minimum_firing_delay_tolerance_ms=0.0`). Run 1's Firefox main-lane timing exactly, 3 lanes × 3 cycles, with Firefox's timer firing-delay tolerance set to zero.

### Setup (controller rulings applied)

- **Fake SGW** (`test/fakes/fake-sgw-server`, in process; not modified): `skewMs: +1300` and `latencyMs: {'*': 150}`, with PlaceBid at 25 000 ms (main) or 45 000 ms (controls). The `/__log` request log is saved per run to correlate PlaceBid arrival. Nothing touches shopgoodwill.com. (Chromium's own GCM client tried to reach Google, per `chrome-stderr.txt`; the probe made no such request.)
- **Chrome:** Playwright's bundled Chromium (Chrome for Testing 153.0.8010.12), spawned as a **plain process** with `--headless --load-extension` and no `--remote-debugging-*`. No driver is attached: an attached DevTools/CDP session keeps a service worker alive, so a driven browser would invalidate the measurement. All Chrome lanes run in one browser, one service worker each.
- **Firefox 157.0.1:** `web-ext run` with a temporary install over RDP, `MOZ_HEADLESS=1`, one Firefox instance per lane. web-ext attaches no toolbox. Firefox skips idle suspension only when `DebugUtils.hasDevToolsAttached(id)`, so suspension applies here, and the positive control confirms it.
- **Unpacked, not packed.** Playwright can't install packed builds, and Firefox release builds load unsigned add-ons only as temporary installs. Chrome's 30 s alarm floor for packed builds doesn't matter here: the only alarm on the snipe path is the wake alarm, set ≥ 5 min ahead. Firefox's alarm code has no floor at all (`parent/ext-alarms.js` calls `nsITimer.init(delay)` directly). **Confirming on a packed build is manual (acceptance A-4).**
- **No visible extension window** in run 1: both browsers run headless, and no extension page, popup or DevTools is opened. The runner study opens popups on purpose; that is the variable it tests.
- **Host:** Windows 11 Pro 10.0.26200, Intel Core Ultra 9 275HX (24 threads), 31 GB RAM, on AC. Other ShopBadwill workers were active on the machine. Total CPU (typeperf, 10 s samples) in run 1: mean 6.4 %, p95 23.7 %, max 43.7 %. That rules out CPU starvation as the cause of the Firefox deferral.

### Source evidence (read-only, from the installed browsers)

Extracted from Firefox 157.0.1 `omni.ja`:

| File | What it says | Consequence |
|---|---|---|
| `parent/ext-backgroundPage.js` | Idle timeout pref `extensions.background.idle.timeout`, default **30 000 ms**, clamped to 100 ms–5 min. `IdleManager.resetTimer()` runs on every `background-script-reset-idle`. Suspension is skipped only for an attached DevTools toolbox, open native-messaging ports, pending listener promises (once) or an active StreamFilter. | Fetches are not a keep-alive reason. A probe without a toolbox is subject to suspension. |
| `modules/ExtensionParent.sys.mjs`, `ParentAPIManager.recvAPICall` | For a non-persistent background context, every parent API call emits `background-script-reset-idle` with `reason: "parentapicall"`. | Any API implemented in the parent resets the 30 s timer. |
| `parent/ext-runtime.js` | `getPlatformInfo: () => Promise.resolve(ExtensionParent.PlatformInfo)`, with no child-side implementation (`child/ext-runtime.js` has none). | **`runtime.getPlatformInfo()` is a parent API call, so it resets the event-page idle timer.** This answers the §1.3 Firefox gap from source; the measurement confirms it. |
| `modules/ExtensionParent.sys.mjs`, `createBrowserElement` | The hidden background `<browser>` gets `docShellIsActive = true` ("unconditionally active frame"). | DOM timers in the event page are not *background-tab* throttled (no 1 s clamp, no budget throttling). The deferral below comes from elsewhere. |
| `parent/ext-alarms.js` | An alarm is one `nsITimer.TYPE_ONE_SHOT` with delay `when − Date.now()` and no minimum. | Firefox has no alarm floor, packed or unpacked. |

**Firefox timer firing-delay tolerance.** Firefox's `TimerThread` (`xpcom/threads/nsTimerImpl.cpp`, `AcceptableFiringDelay()`) gives eligible timers a tolerance of `clamp(delay/8, timer.minimum_firing_delay_tolerance_ms, timer.maximum_firing_delay_tolerance_ms)`. It then bundles wake-ups so that several timers fire together. Both pref names are in this build's `xul.dll`. The maximum behaves like 10 000 ms. Reading the current source alone, plain one-shot DOM timers should be exempt. The measurement says otherwise for this build in this state: setting both prefs to 0 removed every deferral (pref run below). I did not pin down which code path makes these timers eligible. The runner study shows the trigger: the deferral is present while the extension has no window, and absent while an extension popup is open.

## What this changes

1. **Firefox `SnipeHost`: T-116 is required, Phase 4, not conditional.** Its job is to have an extension window open from about T−60 s until the post-read, with `windows.create({type:'popup', focused:false})` holding a `runtime.connect` port as §1.3 describes. Measured: with the window open, the background's own timer is accurate, so the engine's timer can stay in the background on both browsers, and the `SnipeHost` contract (§3.9) stays as written. **Unmeasured risk, for T-116 and A-4:** these runs were headless, where the popup counts as visible and focused. On a real desktop with the screen off, locked, or the popup occluded, Firefox may treat the window as hidden and bring the deferral back. A-4 must check fire error on a headed, packed Firefox at night with the screen off.
2. **User-side Firefox alternative.** `about:config` → `timer.maximum_firing_delay_tolerance_ms = 0` (a float pref, set as `0.0`) removes the deferral for all timers in the whole browser. That costs Firefox's wake-up batching, a power cost on a laptop that is plugged in anyway. An extension cannot set it. It is a candidate optional USER STEP for A-4 and a fallback if T-116's window turns out not to help with the screen off. It is not a substitute for T-116.
3. **`KeepAlive`: keep 20 s, do not raise it to 25 s.** Firefox stretched 20 s heartbeats to as much as 26.9 s through the same deferral. A 25 s interval could exceed the 30 s idle timeout. Only *parent* API calls count on Firefox: `storage.local` writes do not keep the event page alive, so the hold must keep `getPlatformInfo` running through PlaceBid and the post-read.
4. **Tight timer on Chrome: §1.3 as written is sufficient.** A single `setTimeout` from T−60 had p95 4.4 ms, max 4.6 ms. Staged hops gave no gain (p95 4.6 ms), so the engine needs no hop logic for Chrome. On Firefox, hops do not help either (see above).
5. **PlaceBid 20 s abort: keep it.** Chromium 153 did not kill a heartbeat-held worker during a 45 s fetch, so the abort is not what keeps the worker alive. It still bounds the ambiguous window, and a worker that loses its heartbeat dies about 30 s after its last API call, in-flight fetch or not. The restart path (persist `sentAt` → recovery alarm → ambiguous → post-read) recovered 6/6 forced deaths.
6. **Recovery alarm.** A worker that dies mid-fetch is only revived by an alarm. The engine needs a `recover` alarm (here fire + 100 s; on Firefox it may fire up to `min(delay/8, 10 s)` late).
7. **Budget the persist-before-send step.** Writing `sentAt` before the request adds p95 11 ms (Chrome) and 17 ms (Firefox) between the timer and `fetch()`. That is small against the 8 s lead; T-81/T-85 can fold it into the lead.
8. **Wake alarm on Firefox** may arrive up to about 10 s late. Nothing on the snipe path should depend on alarm precision finer than that. The T−5 min wake is fine.
9. **Clock offset.** The estimator and the `oneWay = rtt/2` correction behaved as designed, offset error equal to rtt/2 under the fake's latency model. Real-world latency asymmetry stays a T-74 soak question.

## Deviations and limits

- **Unpacked and temporary installs** (controller ruling). The packed-build alarm floor and fire timing on a packed, headed build are A-4's manual check.
- **Headless** for both browsers, to keep the measurement free of visible windows. Background-context lifecycle is the same headless or headed. Firefox's window-dependent timer deferral may differ headed, which is risk 1 above.
- Run 1 timing is shorter than a real snipe only in the arm-to-wake gap (90 s); wake → fire is the real 5 min.
- The machine was shared with other workers (CPU logged in each run's `cpu.csv`).
- Pilot runs during probe development are not committed. They showed Chrome about 10 ms late while the probe's 5 s ticks ran (hence the tick pause) and Firefox 3–172 ms late with 90 s holds.
