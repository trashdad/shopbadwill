# 06-qa — QA, Testing & Security Lead Proposal

Author role: QA / testing / security specialist. Research date: 2026-10-07. Sources were checked through web search and fetch. I made one read-only request to a public shopgoodwill.com search page and one to its robots.txt. I did not log in or take any account action. Items marked **(unverified)** could not be confirmed from a primary source.

## Research Findings

### A. End-to-end testing of cross-browser extensions

1. **Playwright works for Chromium only, and needs a persistent context.** The official docs load an extension with `chromium.launchPersistentContext(userDataDir, { channel: 'chromium', args: ['--disable-extensions-except=…', '--load-extension=…'] })`. The `chromium` channel supports headless runs. You reach the MV3 service worker with `context.serviceWorkers()` or `waitForEvent('serviceworker')`, and you read the extension ID from the worker URL. The docs say MV3 workers are suspended after about 30 s idle and restarted on demand, and that Playwright keeps the same Worker handle across the restart. The docs also say: "Google Chrome and Microsoft Edge removed the command-line flags needed to side-load extensions," so use Playwright's bundled Chromium. Source: https://playwright.dev/docs/chrome-extensions
2. **Branded Chrome 137+ ignores `--load-extension`.** This comes from a Chromium PSA dated 2025-04-04. Chromium and Chrome for Testing are unaffected. For personal use, "Load unpacked" in developer mode still works. Source: https://groups.google.com/a/chromium.org/g/chromium-extensions/c/1-g8EFx2BBY
3. **Playwright has no official Firefox extension support.** The Playwright extension docs never mention Firefox. A third-party package, `playwright-webextext`, can install temporary Firefox add-ons, but its MV3 support is limited. https://npmjs.com/package/playwright-webextext. The realistic Firefox E2E options are:
   - Selenium/geckodriver `driver.install_addon(path, temporary=True)`. It accepts a directory or a zip. The moz-extension UUID is random on each run. https://www.selenium.dev/documentation/webdriver/browsers/firefox
   - WebDriver BiDi `webExtension.install`. Unsigned add-ons can only be installed temporarily. https://firefox-source-docs.mozilla.org/remote/webdriver-bidi/Extensions.html
   - Puppeteer. It has stable Firefox support through BiDi from v23 (https://hacks.mozilla.org/2024/08/puppeteer-support-for-firefox/). It also has `browser.installExtension(path)`, but the API page says nothing about Firefox support **(unverified on Firefox)**. https://pptr.dev/api/puppeteer.browser.installextension
   - `web-ext run` for manual or smoke runs. It supports `--target firefox-desktop|chromium`, `--firefox-profile`, `--start-url` and `--pref`. https://extensionworkshop.com/documentation/develop/web-ext-command-reference/
4. **Puppeteer is a Chromium alternative.** It uses the `enableExtensions: [path]` launch option or `browser.installExtension()`. You can open the popup with `worker.evaluate('chrome.action.openPopup()')`. https://pptr.dev/guides/chrome-extensions
5. **WXT recommends Playwright as "the only good option" for Chrome extension E2E.** It points Playwright at `.output/chrome-mv3` and says nothing about Firefox E2E. https://wxt.dev/guide/essentials/e2e-testing
6. **Mocking network calls from a service worker in Playwright is experimental.** It needs `PW_EXPERIMENTAL_SERVICE_WORKER_NETWORK_EVENTS=1` and is Chromium-only. Whether it intercepts *extension* service-worker fetches is **unverified**. https://playwright.dev/docs/service-workers-experimental. A safer design is a test-build-only API base URL that points at a local fake ShopGoodwill/Google server, plus a CI check that the production build hardcodes the real origins.
7. **Playwright's Clock API can control page time.** It offers `install`, `fastForward`, `runFor`, `pauseAt` and `setFixedTime`, applies to the whole BrowserContext, and arrived in v1.45. https://playwright.dev/docs/clock. Whether it affects the extension service worker is **unverified**, so inject a `Clock` port instead.
8. **HAR replay.** `routeFromHAR(file, { update })` can record and replay page traffic. The file is written when the context closes, and requests are matched on method plus full URL. https://playwright.dev/java/docs/mock
9. **CI notes.** Headed runs need `xvfb-run` on Linux. Headless runs of the `chromium` channel do not (secondary sources, e.g. https://playwright.dev/docs/browsers). The GitHub Action `kewisch/action-web-ext` handles lint, build and sign with PR annotations: https://github.com/kewisch/action-web-ext

### B. Unit and integration testing

10. **WXT and Vitest.** The `WxtVitest()` plugin swaps the `browser` API for the in-memory `@webext-core/fake-browser`. Call `fakeBrowser.reset()` in `beforeEach`. Storage does not need mocking. https://wxt.dev/guide/essentials/unit-testing. The import path has changed between versions: the top-level `wxt/testing` is deprecated, and current docs show `wxt/testing/vitest-plugin` and `wxt/testing/fake-browser`. Check against the pinned version.
11. **fake-browser coverage.** It implements alarms "as in production, except for `onAlarm`," which you trigger with `onAlarm.trigger()`. Notifications `create/clear/getAll` work, with click and close events triggered manually. Storage local/sync/session/managed and tabs/windows are fully implemented. `runtime.sendMessage` fires `onMessage` listeners. The docs say nothing about **identity** or **permissions**, so assume those need hand-written fakes. https://webext-core.aklinker1.io/fake-browser/implemented-apis
12. **Vitest fake timers** cover `setTimeout`, `Date` and `performance.now`, and are built on @sinonjs/fake-timers. `vi.setSystemTime` pins "now". https://vitest.dev/guide/mocking/timers. Fake timers do not drive real `chrome.alarms`, so trigger alarm handlers directly.
13. **MSW `setupServer` (msw/node) intercepts native fetch in Node 18+.** It works for unit and integration tests of the HTTP clients, but not inside a real extension worker. https://mswjs.io/docs/integrations/node
14. **Older alternatives.** jest-chrome and sinon-chrome are Chrome-only mocks. WXT does not officially support Jest, so prefer Vitest with fake-browser.

### C. Platform constraints that drive test design

15. **Chrome alarms.**
   - The minimum delay or period is 0.5 min, and Chrome "may delay them an arbitrary amount more."
   - **Unpacked extensions have no rate limit.** Tests on unpacked builds can therefore pass timings that production would miss.
   - Alarms run during device sleep but do not wake the device. A missed alarm fires once on wake.
   - `persistAcrossSessions` is Chrome 150+ and defaults to true. Other browsers do not support it.
   - Source: https://developer.chrome.com/docs/extensions/reference/api/alarms
   - Conclusion: alarms are fine for the daily job but **too coarse for last-second sniping**. Use an alarm a few minutes before the end, then an in-memory timer held alive by periodic extension API calls.
16. **Chrome service worker lifecycle.** The worker is terminated after 30 s idle, if one event or API call runs longer than 5 min, or if a fetch response takes more than 30 s. Since Chrome 110, extension API calls reset the idle timer. https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle
17. **Firefox MV3 has no `background.service_worker`.**
   - It uses non-persistent event pages (`background.scripts`). WXT and similar tools emit the right manifest for each browser. https://blog.mozilla.org/addons/2022/10/31/begin-your-mv3-migration-by-implementing-new-features-today/
   - The idle timeout is about 30 s according to a forum post, and the pref `extensions.background.idle.timeout` controls it. An attached DevTools toolbox prevents termination, which can hide bugs during manual testing.
   - Source: https://discourse.mozilla.org/t/how-to-stop-a-background-script-from-going-idle-in-mv3/128327
18. **Firefox MV3 host permissions are opt-in and revocable.**
   - Content scripts may not run until the user grants the site.
   - `permissions.request` only works from a user gesture.
   - Use `permissions.contains`, `onAdded` and `onRemoved`.
   - Host permissions have appeared in the install prompt since Fx127.
   - Source: https://developer.mozilla.org/docs/Mozilla/Add-ons/WebExtensions/manifest.json/host_permissions
19. **Chrome 148+ exposes a native `browser` namespace.** Native promise-returning `onMessage` listeners make `webextension-polyfill` a no-op there. https://developer.chrome.com/docs/extensions/develop/concepts/browser-namespace

### D. Signing, review and distribution

20. **Firefox release and beta builds require Mozilla-signed add-ons.** For personal use, `web-ext sign --channel unlisted --api-key … --api-secret …` signs for self-distribution. Developer Edition, Nightly and ESR can disable signature checks. https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/
21. **AMO source-code requirement.** For bundled or minified code, AMO requires source plus build instructions so a reviewer can rebuild and diff the output. Build tools must be open source. Obfuscation is banned even off AMO. I found no exemption for unlisted add-ons. `web-ext sign` has `--upload-source-code`. https://extensionworkshop.com/documentation/publish/source-code-submission/
22. **Firefox data-collection declaration.** New AMO submissions since 2025-11-03 must declare `browser_specific_settings.gecko.data_collection_permissions`, using `["none"]` if nothing is collected. MV3 also needs the gecko ID to sign. https://extensionworkshop.com/documentation/develop/firefox-builtin-data-consent/
23. **`web-ext lint`.** It wraps addons-linter and supports `--warnings-as-errors`, `--output json` and `--self-hosted`, which suppresses AMO-listing messages. https://extensionworkshop.com/documentation/develop/web-ext-command-reference/
24. **Chrome Web Store.** This only matters if the extension is ever published.
   - The July 2026 policy update requires data collection to be strictly necessary for the single purpose and fully disclosed: https://developer.chrome.com/blog/cws-policy-updates-2026
   - Remote code is banned, including interpreters for fetched commands. A privacy policy is required if any user data is handled: https://developer.chrome.com/docs/webstore/program-policies/policies
   - I found nothing that explicitly bans auction-bidding extensions, and eBay snipers such as Bid-O-Matic and PowerSniper are listed.

### E. Security-relevant facts about ShopGoodwill and Google

25. **ShopGoodwill is an Angular 15.2.9 SPA.** I checked this with one read-only request on 2026-10-07. The server HTML for a search page contains 25 `<app-product-loader>` skeletons, so listings render client-side from the API. The page loads Google reCAPTCHA scripts, which makes automated password login undesirable or fragile. Content scripts need a MutationObserver and must survive SPA navigation. Selectors such as `.feat-item` will drift.
26. **robots.txt** asks crawlers for `Crawl-delay: 120` and disallows `/shopgoodwill/`, `/checkout/` and `st=` listing URLs (fetched 2026-10-07). Any canary or polling job should be gentle, with jitter, backoff, and a circuit breaker on 403/429.
27. **The unofficial buyer API**, from the open-source shopgoodwill-scripts client:
   - Base URL: `https://buyerapi.shopgoodwill.com/api/`
   - Endpoints: `SignIn/Login`, `Search/ItemListing`, `itemDetail/GetItemDetailModelByItemId/{id}`, `Favorite/AddToFavorite?itemId=`, `Favorite/GetAllFavoriteItemsByType?Type=open|close|all`, `Favorite/Save` (notes), `SaveSearches/GetSaveSearches`, `itemBid/ShowBidModal?itemId=` (sellerId), `ItemBid/PlaceBid {itemId,bidAmount,sellerId,quantity}`, `itemDetail/CalculateShipping`.
   - Auth uses `Authorization: Bearer`. Login "encrypts" credentials with AES-CBC using a key and IV hardcoded in the client, which is obfuscation only.
   - The client has no refresh-token handling, no rate limiting and no 403 handling.
   - The search API returns 403 when the search text contains quotes.
   - Source: https://github.com/scottmconway/shopgoodwill-scripts (README and `shopgoodwill.py`)
   - All of this is undocumented and may change: **(unverified against the live API by me; I made no authenticated calls)**.
28. **Native ShopGoodwill features worth reusing rather than duplicating:** built-in proxy bidding, favorites under "My ShopGoodwill", saved searches, and "personal shopper" email alerts for new matches. https://blog.shopgoodwill.com/english/the-ultimate-guide-to-bidding-buying, https://apps.apple.com/app/id1590146817
29. **Unknowns about the site itself.** I could not find ShopGoodwill's ToS stance on third-party automated bidding, whether late bids extend an auction (soft close), or the increment table. The Canadian Goodwill FAQ warns that bids in the last seconds "may not be processed."
30. **Google Calendar.**
   - `reminders.overrides` allows at most 5 entries, with method `popup` or `email`.
   - The client can supply an event `id` (base32hex, 5–1024 chars), which gives idempotent inserts: a duplicate returns a conflict.
   - Narrow scopes exist: `calendar.app.created` covers only calendars the app creates, and `calendar.events.owned` covers events on owned calendars. Google says to use the narrowest scope. https://developers.google.com/workspace/calendar/api/auth
   - Calendar scopes are "sensitive" and need verification for a published app. An app left in **Testing** gets refresh tokens that **expire after 7 days** (secondary sources).
31. **Google OAuth differs by browser.**
   - `identity.getAuthToken` is Chrome-only.
   - Firefox has only `getRedirectURL` and `launchWebAuthFlow`. Interactive mode must start from a user action.
   - Google has rejected Firefox's `*.extensions.allizom.org` and moz-extension redirect URIs in reported cases. Firefox 86+ also allows a loopback `http://127.0.0.1/mozoauth2/…` redirect, but whether Google accepts it is **unverified**.
   - Source: https://developer.mozilla.org/docs/Mozilla/Add-ons/WebExtensions/API/identity/launchWebAuthFlow, https://discourse.mozilla.org/t/how-to-integrate-google-oauth-for-calendar-access-in-firefox-extension-previously-successful-in-chrome/134818
   - This is the single biggest cross-browser risk and needs a Phase-0 spike.
32. **Token storage.**
   - `storage.local` is unencrypted on disk and readable by any code in the extension context.
   - `storage.session` lives in memory and is cleared on browser restart. By default content scripts cannot read it (trusted contexts only).
   - `storage.sync` copies data to the Google account, so never put tokens there.
   - Encrypting a value with a key that sits in the same storage only protects against reading files at rest.
   - Source: https://github.com/w3c/webextensions/blob/main/proposals/secure-storage.md
   - Trade-off: a daily job that runs after a browser restart needs a persisted ShopGoodwill token, or it must degrade gracefully.

### F. Testing implications I recommend

- Use a **ports-and-adapters** design (`Clock`, `Http`, `Storage`, `Alarms`, `SgwApi`, `CalendarApi`) so most logic is pure and unit-testable on fake time.
- Write **zod-style schemas** for every SGW response. Validate sanitized recorded fixtures in contract tests, and validate live responses at runtime as well. **Fail closed**: never favorite or bid on data that fails validation.
- Build **DOM fixtures** by capturing the *rendered* DOM after Angular hydration with Playwright, then sanitize it. Raw server HTML is only skeletons.
- Add a **live canary** as a scheduled GitHub Action: anonymous, read-only, one search plus one page render. It checks the schemas and the selectors and opens an issue on drift. It never uses credentials and never writes.
- **Test-only hooks** (time travel, trigger alarm, fake base URL) must be compiled out of production. Add a CI step that greps the production bundle to prove it.
- **No automated test ever favorites, bids, or writes to a real Google calendar.** Real-account checks are a manual acceptance script that runs in dry-run first.

**Lessons:**
1. Local snipers only fire if the browser is awake. Surface "missed" honestly.
2. Store max bids locally, never in a third-party cloud.
3. Dry-run and friend-list features are proven useful.
4. Auction groups are a well-liked advanced feature.
5. Bidguard shows that accident prevention is a real user need.

## Quality-of-Life Ideas

1. **[MVP] Dry-run / simulate mode, on by default for every automation.** It shows exactly what would be favorited, calendared or bid before anything touches the account, so users build trust safely.
2. **[MVP] Kill switch plus "disarm all" in the popup, with a badge showing the number of armed snipes.** One click stops every state-changing action, the most important safety valve.
3. **[MVP] Append-only activity/audit log page with JSON/CSV export and one-click undo** for favorites and calendar events. Every autonomous action is visible and reversible, and the log doubles as debugging evidence.
4. **[MVP] "Why hidden / why highlighted?" chip on each card, plus a "N hidden — show" toggle.** Rule engines confuse users when they can't see which rule fired.
5. **[MVP] One-click "hide this seller/location" and negative-keyword rules from a listing card.** Rules come from real browsing instead of a settings form, as in the eBay and Buyee blocklist scripts.
6. **[later] Health/status page.** Shows last successful daily run, ShopGoodwill and Google token status, and the drift result from runtime schema/selector checks. Flags breakage before a missed auction does.
7. **[later] Rule tester / preview.** Paste a search or run a rule and see which current listings would match before saving. TDD for the user's own rules.
8. **[later] Shipping-inclusive "true total" display and filter, using the user's ZIP.** ShopGoodwill shipping varies by location and often decides whether an item is a deal.
9. **[later] Calendar events that stay in sync.** Update or delete the event when an item is won, lost, removed or unfavorited, and put the item link, current price and max bid in the description. Avoids stale reminders.
10. **[later] New-since-last-run digest notification, deduped by itemId.** Also detects relists through a title and image hash, which shopgoodwill-scripts notes is a gap.
11. **[later] Settings backup and restore (export/import JSON).** Optional `storage.sync` for rules only, never tokens.
12. **[stretch] Snipe groups: "win at most one of these."** Proven on bidbag and Bid-O-Matic, and stops accidentally winning three identical lamps.
13. **[stretch] Friend list: never outbid these users.** An existing shopgoodwill-scripts feature for households and friends.
14. **[stretch] Sold-price comps from closed ShopGoodwill auctions next to the current bid.** Helps choose a sane max bid.

## Fable Prompt

You are the lead planner for **ShopBadWill**. It is an MIT-licensed, greenfield repo containing only README and LICENSE. The product is a **Chrome and Firefox** extension that helps one user shop **shopgoodwill.com**, Goodwill's online auction site. Produce an **implementation plan, not code**.

An orchestrator will execute your plan by dispatching parallel worker agents with isolated context, then testing extensively. Every task must be buildable and verifiable by an agent that sees only that task, the repo, and your shared contracts.

### Functional requirements
1. **Listing overlay:** on search and listing pages, highlight or hide visible listings according to user-defined rules (keywords, negative keywords, seller/location, price, time left, etc.).
2. **Autonomous daily check:** once a day, run the user's watch rules (saved searches) without the user present.
3. **Favorite** matching items on the user's ShopGoodwill account.
4. **Google Calendar:** add each matched auction's end time as an event, with popup reminders **60, 15 and 5 minutes** before the end.
5. **Nice-to-have:** bid for the user, or **snipe** in the final seconds up to a max bid the user sets in advance.

Also propose tagged (MVP/later/stretch) quality-of-life features, including at least dry-run mode, an audit log with undo, "why hidden/highlighted" explanations, a health page, and a kill switch.

### Researched facts (October 2026). Items marked ⚠ are unverified and need a spike.

**The site.**
- shopgoodwill.com is an Angular 15 single-page app that loads reCAPTCHA. Listings render client-side after skeleton loaders, so content scripts must handle async rendering and in-app navigation, and selectors will drift.
- Data comes from an undocumented JSON API at `https://buyerapi.shopgoodwill.com/api/`. An open-source client (github.com/scottmconway/shopgoodwill-scripts) uses these endpoints:
  - `POST Search/ItemListing`
  - `GET itemDetail/GetItemDetailModelByItemId/{id}`
  - `GET Favorite/AddToFavorite?itemId=`
  - `POST Favorite/GetAllFavoriteItemsByType`
  - `POST SaveSearches/GetSaveSearches`
  - `GET itemBid/ShowBidModal?itemId=` (returns sellerId)
  - `POST ItemBid/PlaceBid {itemId,bidAmount,sellerId,quantity}`
  - `POST itemDetail/CalculateShipping`
- Auth uses `Authorization: Bearer <token>`. Login "encrypts" credentials with a hardcoded key, which is obfuscation only.
- Treat every endpoint and field as unverified ⚠. The site has built-in proxy bidding, favorites and saved searches. robots.txt asks for a 120-second crawl delay.
- Unknown ⚠: the ToS stance on automated bidding, and whether late bids extend an auction.

**Browsers.**
- Chrome MV3 runs a background service worker that is killed after about 30 s idle. Extension API calls reset that timer.
- Firefox MV3 does **not** run `background.service_worker`. It uses non-persistent event pages (`background.scripts`).
- Firefox MV3 host permissions are user-revocable and opt-in. Content scripts may not run until the user grants access, and `permissions.request` requires a user gesture.
- `alarms` has a 30-second minimum and "may delay an arbitrary amount." That suits the daily job but is **not precise enough for sniping**. Unpacked builds skip the minimum, so tests can pass where production fails.
- Alarms do not wake a sleeping machine. The browser must be running, as with eBay snipers like PowerSniper.
- `identity.getAuthToken` is Chrome-only. Firefox needs `launchWebAuthFlow`, and Google has rejected Firefox redirect URIs in reported cases ⚠.
- Google OAuth apps left in "Testing" get refresh tokens that expire after 7 days.
- Narrow Calendar scopes exist: `calendar.app.created` (a dedicated calendar) and `calendar.events.owned`.
- Events allow at most 5 reminder overrides and a client-supplied `id`, which makes inserts idempotent.

**Distribution.**
- Personal use first: Chrome "Load unpacked"; Firefox release builds require signing via `web-ext sign --channel unlisted`.
- AMO requires source and reproducible build instructions for bundled code.
- New Firefox add-ons must declare `browser_specific_settings.gecko.data_collection_permissions`.

**Test tooling.**
- WXT (wxt.dev) builds both browsers from one source. Its Vitest plugin provides an in-memory `fakeBrowser` covering storage, alarms (trigger `onAlarm` manually), runtime, tabs and notifications. Identity and permissions need hand-written fakes.
- Playwright supports extension E2E **only in Chromium**. It uses `launchPersistentContext` with `--load-extension` on its bundled Chromium, and the `chromium` channel works headless. Branded Chrome ignores the flag. The service worker is reachable through `context.serviceWorkers()`. Routing that worker's fetches is experimental ⚠.
- There is no Playwright extension support for Firefox. The options are Selenium/geckodriver `install_addon(temporary=True)`, WebDriver BiDi `webExtension.install`, Puppeteer ⚠, or `web-ext run` for smoke tests.
- `web-ext lint --warnings-as-errors` runs Mozilla's linter.
- MSW intercepts fetch in Node, not inside a real extension worker.

### Engineering principles (non-negotiable)

**TDD everywhere.** Each task lists failing tests first, then implementation, then gate commands. A task is done only with green gates and pasted evidence.

**Ports and adapters.**
- Domain logic (rule engine, bid and increment math, snipe state machine, calendar-event builder, scheduler) depends only on injected interfaces: `Clock`, `Http`, `Storage`, `Alarms`, `Notifier`, `SgwApi`, `CalendarApi`. Browser glue stays thin.

**Test pyramid in every phase.**
1. Static checks: TypeScript strict, ESLint with unsafe-DOM rules, `web-ext lint`, and a manifest-permissions snapshot that fails on any new permission.
2. Unit tests: Vitest, fake timers, and property tests for money and time math.
3. Contract tests: schema validation of sanitized, recorded API fixtures. The same schemas validate live responses at runtime and **fail closed**.
4. Integration tests: fakeBrowser plus MSW.
5. Content-script tests against sanitized, *rendered* DOM captures.
6. Offline Chromium E2E against a fake ShopGoodwill server and a fake Google server.
7. A thinner Firefox E2E or smoke lane.
8. A **scheduled, read-only, anonymous live canary** that detects API and DOM drift. It never logs in and never writes.
9. A manual acceptance script for the real account.

**No live writes in automated tests.** No automated test may favorite, bid, or touch a real calendar. Test-only hooks (time travel, alarm triggers, base-URL override) must be compiled out of production, and a CI check must prove it.

### Safety and security requirements

**Permissions.** Request least privilege: only shopgoodwill.com, buyerapi.shopgoodwill.com and the Google API hosts. Make the permissions for opt-in features optional.

**Credentials and tokens.**
- Never store the user's raw password. Prefer reusing the session the user already has in the browser. How the site stores its token is unknown ⚠, so plan a spike.
- Decide where ShopGoodwill and Google tokens live (`storage.session` or `storage.local`) and how expiry works.
- Degrade gracefully when a token is missing: still search, queue the favorites, and notify the user.

**Untrusted input.**
- Treat all listing text as attacker-controlled. Use no `innerHTML`, and put injected UI in Shadow DOM.
- The background must validate the sender of every message. Content scripts must never trigger state-changing actions.

**Bidding.** It ships **disabled** and is gated by all of the following:
- Dry-run by default.
- Explicit per-item arming with a typed max bid.
- A per-item cap and a daily or weekly spend cap.
- Pre-flight checks: item still open, price below max, valid schema, bounded clock skew.
- Idempotency, so a restarted worker never double-bids.
- A one-click kill switch.
- An append-only local audit log of every favorite, calendar write and bid. The log must contain no secrets.

**Other.** No telemetry and no remote code.
